# Phase 17 — Frontend Payment Placeholder (Step 06): notes for future sessions

Persisted for continuity. See also `README.md` (project status) and
`docs/phase-16-review-step-notes.md`.

## What this phase delivered

- `components/registration/ConfirmStep.tsx` (rewritten) — a real,
  two-phase Step 06, both phases local `useState` (not wizard/reducer
  state — this is within-step UI navigation, not registration data):
  1. **Summary** — "Registration Amount" as a headline figure plus the
     same `PricingBreakdown` component `PackageStep`/`ReviewStep` already
     use (labelled "Payment Summary" here), so the number here can never
     drift from what the participant already reviewed. The "Continue to
     Payment" CTA is disabled until `state.review.acceptedTerms` is true
     — a defensive re-check for a participant who reached Confirm by
     jumping directly via `RegistrationProgress`'s step indicator rather
     than Review's own "Proceed" gate.
  2. **Demo Payment** — the brief's own "Demo Payment — Frontend Only"
     panel: plain-language statement that no real payment is processed,
     the brief's exact sentence "Payment integration will be connected
     during backend integration," and a single "Simulate Successful
     Payment (Demo)" action. A "Back to Summary" link returns to phase 1
     without losing any wizard state.
- `lib/registration/state.ts` (edited) — `CONFIRM_REGISTRATION`'s
  `paymentStatus` changed from `"demo-pending"` to `"demo-complete"`. See
  the truth-mode/decisions notes below for why.

## Truth-mode audit

- **No Razorpay call, no API route, no real transaction — unchanged.**
  This step still only ever dispatches a local reducer action
  (`CONFIRM_REGISTRATION`) and calls `router.push`; nothing here reaches
  a network.
- **No payment ID of any kind is generated or shown.** The brief says
  "Do not create fake real payment IDs" — this build doesn't create *any*
  payment ID, real-looking or otherwise. The only identifier anywhere in
  this flow is `CONFIRM_REGISTRATION`'s existing mock **registration**
  ID (`AFF26-DEMO-XXXXXX`, unchanged since Phase 02) — a record of the
  registration, not a claimed payment transaction — and the Demo Payment
  panel says so explicitly ("No payment ID is generated by this demo").
- **"Do not claim actual payment"** — every piece of copy in the
  Demo Payment phase is phrased as simulation, never completion: "This
  screen simulates what a payment step will look like," "Simulate
  Successful Payment (Demo)," "this button does not contact any payment
  provider." Nothing says "Payment Successful" or similar without the
  word "Demo"/"Simulate" attached.
- **The brief's required sentence is reproduced verbatim**: "Payment
  integration will be connected during backend integration."
- **The registration amount is not recomputed independently** — same
  `state.pricing` object as Package/Review, so Phase 15's Chess-only fix
  and Base/Food/Accommodation decomposition, and every `[VERIFY WITH
  ORGANIZER]` assumption, all carry through to this final screen exactly
  as shown earlier in the wizard.

## Decisions worth knowing about

- **"navigate to /success" was interpreted as the existing
  `/register/success` route**, not a new top-level `/success` page.
  `app/register/success/page.tsx` (Phase 02) reads `useRegistration()`,
  which only works inside `RegistrationProvider` — scoped to
  `/register/**` by `app/register/layout.tsx`. A bare `/success` route
  outside that subtree would need its own way to read the confirmation
  state (a second provider, a query param, sessionStorage, ...), which is
  a real architectural decision the brief doesn't ask this phase to make.
  Reusing the existing route keeps `ConfirmStep`'s own change scoped to
  "build the payment placeholder," not "restructure where confirmation
  data lives." If a bare `/success` URL is wanted later, that's a small,
  separate, explicit decision for whoever owns the Success/pass phase.
- **`paymentStatus` becomes `"demo-complete"` (not `"demo-pending"`) once
  the demo-success button is pressed.** Phase 02's original single-button
  Confirm had no payment step at all, so "pending" was the honest word
  for what hadn't happened yet. Now that a (simulated) payment step
  exists and this action only fires after it "succeeds," `"complete"` is
  the accurate word for that same moment — nothing about what actually
  happens changed (still frontend-only, still no real transaction),
  only which of the two already-existing `PaymentStatus` values
  correctly describes it. Note: `app/register/success/page.tsx` doesn't
  actually read `state.confirmation.paymentStatus` yet — it hardcodes
  "Frontend Demo / Payment Integration Pending" as static text — so this
  change has no visible effect until a future Success-page phase wires
  the field in. Left as-is since building that page is explicitly out of
  scope for Step 06.
- **The two-phase split is local `useState`, not a new wizard step.**
  The project brief's six named steps (01–06) are unchanged; "Demo
  Payment" is a sub-screen *within* Step 06, not a seventh step —
  `RegistrationProgress`'s six-circle indicator, `STEP_META`, and
  `REGISTRATION_STEPS` were all left untouched.
- **The "Continue to Payment" gate reuses `state.review.acceptedTerms`
  directly** rather than adding a new `isConfirmStepValid` to
  `validation.ts` — there's nothing else to validate at this step (no
  form, no selection), so a second wrapper function would add a layer of
  indirection without doing more than the boolean check itself already
  does inline, unlike Events/Package/Review's gates which each wrap a
  real (if simple) rule about their own step's data.
- **`OrnamentalFrame`'s Demo Payment panel is emphasized with
  `ring-1 ring-warm-gold`, not a `border-*` className override.**
  `OrnamentalFrame` already bakes in its own `border-antique-gold/30`
  class; layering a second `border-*` utility on top of it risks losing
  depending on Tailwind's generated stylesheet order (the same
  cascade-order fragility `EventCard`'s Phase 13 "selected" ring already
  documents) — a `ring` is a different CSS property (`box-shadow`), so it
  always layers additively regardless of source order.

## Still-open limitation (unchanged since Phase 02)

Same npm-registry-unreachable constraint as every prior phase. Verified
this phase with the same method as always: strict `tsc --noEmit` over the
pure-logic file set (zero errors — `state.ts`'s `CONFIRM_REGISTRATION`
change joins this pass; `ConfirmStep.tsx` itself is a `.tsx` client
component and, like every other step component, isn't part of this
pure-logic list), esbuild syntax-check (zero errors, 66 `.ts`/`.tsx`
files — unchanged from Phase 16, since this phase edited existing files
rather than adding new ones), and a script confirming all 146 `@/...`
imports resolve (up from 144 — `ConfirmStep.tsx` gained two new import
paths, `PricingBreakdown` and the design-system barrel). **Not yet seen
in a real browser.** This phase's highest-risk surface: the phase
transition itself (does "Continue to Payment" actually swap to the Demo
Payment panel without losing scroll position awkwardly; does "Back to
Summary" return cleanly), whether the disabled-state message under
"Continue to Payment" reads correctly, and the actual navigation to
`/register/success` on demo-success — plus, as `docs/phase-16-review-
step-notes.md` already flagged, whether jumping to Confirm directly via
the progress indicator (bypassing Review's own "Proceed" gate) correctly
shows the disabled-with-reason "Continue to Payment" state rather than
silently allowing it through.

## Superseded by Phase 41 (kept here for history, not rewritten)

Everything above describes Step 05/06 as it existed from this phase
through Phase 40. **Phase 41 replaced the entire two-phase "Payment"/
"Demo Payment" design this doc describes** with a real submission to a
Google Sheets + Apps Script backend — there is no "Continue to Payment"
button, no "Demo Payment — Frontend Only" panel, and no
`paymentStatus`/`PaymentStatus` field anymore; `CONFIRM_REGISTRATION`
now carries a real, server-issued `registrationId`, not a client-generated
mock one. See `components/registration/ConfirmStep.tsx`'s current doc
comment, `docs/phase-41-confirm-registration-google-sheets-notes.md`, and
`docs/google-sheets-setup.md`. This file is left as-is (not rewritten) as
a historical record of what Step 05/06 looked like before that change —
per the same precedent Phase 33/37 set for annotating rather than erasing
earlier phases' notes.
