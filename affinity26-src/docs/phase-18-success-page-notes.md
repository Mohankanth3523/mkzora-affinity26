# Phase 18 — Registration Success Experience (/success): notes for future sessions

Persisted for continuity. See also `README.md` (project status) and
`docs/phase-17-confirm-step-notes.md`.

## What this phase delivered

- `app/success/page.tsx` (new) — a Server Component shell (so this route
  can export `metadata`) wrapping the real content in its own
  `RegistrationProvider`.
- `components/success/RegistrationPass.tsx` (new) — the actual pass UI:
  a prominent "this is a demo, not a real confirmation" banner, the
  "Your Tale Has Begun" heading (one of the project brief's own approved
  design-copy examples), and an `OrnamentalFrame` pass card showing
  Registration ID / Participant / College / Events / Amount / Payment
  Status, a hand-drawn deterministic QR-shaped placeholder captioned
  "Demo QR — verification will be connected later" (the brief's exact
  wording), and three actions: Download Pass, Print, Back to Home.
- `app/register/success/page.tsx` (rewritten) — the Phase 02 placeholder
  that used to live at this path now just `redirect()`s to `/success`,
  so any existing link/bookmark still works. `components/registration/
  ConfirmStep.tsx` (edited) — its demo-success handler now
  `router.push("/success")` instead of `/register/success`.

## Truth-mode audit

- **Nothing on this page is computed independently.** Registration ID,
  participant, college, events, amount, and payment status are all read
  straight from `state.confirmation`/`state.participant`/
  `state.selectedEvents`/`state.pricing` — the same state Package/Review/
  Confirm already showed. The Amount line keeps the same "Estimate —
  subject to organizer confirmation" caveat it's carried since Phase 15,
  because nothing about the underlying source-data ambiguity (base
  package/unlisted-events, §5/§15) resolved just because the wizard
  reached its last screen.
- **"Do not represent mock registration as an actual registration"** is
  handled three separate ways, deliberately redundant: (1) a page-level
  banner above the pass card, in plain sentences, not fine print; (2) a
  small "Demo — Not a Real Pass" tag printed directly on the pass card
  itself, so a screenshot of just the card still carries the disclosure;
  (3) the downloaded/printed artifact (see below) repeats the same
  banner and tag. Payment Status is labelled
  `"Demo Payment Simulated — Not a Real Transaction"`, never a bare
  "Paid"/"Confirmed"/"Successful".
- **The QR placeholder is genuinely fake, and says so.** `QR_GRID` is a
  hardcoded boolean matrix (not a real QR encoding of anything, and not
  generated by a QR library — none is part of this project's
  dependencies) — it exists only to be visually recognizable as "a QR
  code goes here," captioned with the brief's exact required text: "Demo
  QR — verification will be connected later." It's built from a fixed
  array, not `Math.random()`, so server and client render identically
  (no hydration mismatch risk).
- **No fake payment ID exists anywhere on this page.** The only
  identifier shown is the mock **registration** ID
  (`AFF26-DEMO-XXXXXX`, unchanged since Phase 02) — a record of the
  registration, never presented as a payment transaction reference.

## Decisions worth knowing about

- **`/success` is a real, new top-level route — not the interpretation
  Phase 17 made.** Phase 17 kept `router.push("/register/success")`
  because building the real success page was explicitly out of that
  phase's own scope, and reasoned that `/register/success` could keep
  reading `useRegistration()` "for free" via `app/register/layout.tsx`'s
  existing `RegistrationProvider`. Now that *this* phase's job is
  specifically to build `/success`, the fix turned out simpler than
  Phase 17 assumed: `RegistrationProvider` is just a plain component —
  wrapping it fresh around this page's own content works exactly the
  same way, because it hydrates from `localStorage` (the same
  `affinity26.registration.v1` key, `lib/registration/storage.ts`) on
  mount regardless of which page instantiated it. No provider
  restructuring, second reducer, or shared state was needed — just one
  more `<RegistrationProvider>` wrapping one more subtree, the same
  pattern already used for `/register/**`.
- **"Download Pass" produces a self-contained `.html` file, not a PDF or
  image.** No PDF/canvas/image library (`jspdf`, `html2canvas`, etc.) is
  part of this project's dependencies, and this sandbox can't reach the
  npm registry to add and verify one — so rather than adding an
  unverified dependency (or fabricating a fake "PDF" that's actually
  something else), "Download" builds a small standalone HTML document
  (`buildPassHtml()`, pure string templating + a `Blob`/`URL.
  createObjectURL` download — both plain browser APIs, no new
  dependency) that repeats the same demo disclosures, the pass details,
  and the QR caption. A caption under the buttons says plainly what it
  actually is: "saves a demo copy as an HTML file — a printable pass
  design will be available once backend integration is complete." This
  is flagged as the one place this phase's "premium" ambition is capped
  by the sandbox's dependency constraint, not a truth-mode content
  decision — a future phase adding `html2canvas`/`jspdf` (verified on a
  machine with real npm access) could upgrade this to a styled
  image/PDF without changing what data it contains.
- **"Print" is `window.print()`, with `print:` Tailwind variants on the
  pass card and action row** (light background/dark text on the card
  when printed, buttons/banner hidden) so the printed page is legible on
  paper rather than printing the dark on-screen theme verbatim. This
  phase deliberately did **not** touch the shared `Navbar`/`Footer`/
  `AtmosphereBackground` components to hide them during print — that
  would mean editing three global layout components used by every page
  in the app for the sake of one page's print output, which reads as
  overreach for a phase scoped to "build `/success`." A future phase
  could add `print:hidden` to those three components in about three
  lines if a fully chrome-free print output is wanted.
- **A `mounted` gate delays the "no registration found" empty state by
  one render.** `RegistrationProvider` hydrates from `localStorage`
  inside its own `useEffect`, which only fires after mount — so the very
  first client render always shows `confirmation: null` (matching SSR,
  to avoid a hydration mismatch) even when a real mock confirmation
  exists in storage. Without a gate, a participant who just finished
  Step 06 would see a flash of "No registration found" before the real
  pass appeared. This is a best-effort fix (a local `useState`/
  `useEffect` "have we mounted yet" flag, not a guaranteed-race-free
  one) — see the still-open limitation below for why it couldn't be
  fully verified.
- **The old `/register/success` path redirects rather than being
  deleted**, so any existing bookmark or hardcoded link (there were none
  found in this codebase, but external ones can't be ruled out) still
  resolves to the real page instead of 404ing.

## Still-open limitation (unchanged since Phase 02)

Same npm-registry-unreachable constraint as every prior phase. Verified
this phase with the same method as always: strict `tsc --noEmit` over
the pure-logic file set (zero errors — this phase added no new
pure-logic `.ts` files, only `.tsx` components, so the checked file list
itself is unchanged from Phase 16), esbuild syntax-check (zero errors,
68 `.ts`/`.tsx` files, up from 66 — two new files, `app/success/page.tsx`
and `RegistrationPass.tsx`), and a script confirming all 150 `@/...`
imports resolve (up from 146). **Not yet seen in a real browser** — this
phase is a strong candidate for that gap mattering: the `mounted`-gate
hydration timing described above, whether `window.print()`'s output
actually looks right with the `print:` variants applied, whether the
`Blob`/`URL.createObjectURL`/synthetic-`<a>`-click download pattern
actually triggers a save dialog in real browsers (it's a standard,
widely-used pattern, but untestable here), and whether the QR placeholder
SVG renders at a legible size on a phone. A real click-through — finish
the wizard, land on `/success`, confirm the pass shows correct data
immediately with no flash of the empty state, try Download and Print,
then reload `/success` directly (fresh page load, not a client
navigation) and confirm the pass still appears — is the single most
valuable manual test this project has accumulated a need for so far.

## Superseded by Phase 41 (kept here for history, not rewritten)

This phase built `/success` around a `state.confirmation` that was always
a *mock* record — a client-generated ID, and a `paymentStatus` that could
only ever mean "demo." **Phase 41 made registration submission real**
(a Google Sheets + Apps Script backend — see
`docs/phase-41-confirm-registration-google-sheets-notes.md` and
`docs/google-sheets-setup.md`), so `state.confirmation` is now only ever
set after a genuinely confirmed submission. As a direct result, this
page's old "This is a frontend demo, not a real confirmation" banner, its
"Demo — Not a Real Pass" card badge, and its "Payment Status" row are all
gone as of Phase 41 — they described the mock-only reality this phase
built for, which no longer applies. **The QR placeholder is the one
exception, deliberately kept exactly as this phase built it** — see
`components/success/RegistrationPass.tsx`'s current doc comment: the QR
genuinely still encodes and verifies nothing, so "Demo QR — verification
will be connected later" is still accurate and was left untouched. This
file is left as-is (not rewritten) as a historical record of what
`/success` looked like before that change, per the same precedent
Phase 33/37 set.
